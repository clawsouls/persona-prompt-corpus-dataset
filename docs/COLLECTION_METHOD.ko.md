# 수집 방법

## 모집단과 검색

경로 기반 검색 5종으로 GitHub 공개 저장소를 훑었다 — `persona` · `agent` · `role` ·
`identity` · `soul`.

**왜 인기도 표본이 아니라 경로 검색인가.** 성숙한 인기 저장소를 걸러낸 표본
(포크 아님 · 기여자 2명 이상 · OSI 라이선스 · 커밋 271개 이상 등)에서는 이런 파일이
구조적으로 잡히지 않는다. 그런 저장소 9,975곳을 스캔했을 때 파일명 패턴에 걸린 것은
42곳(0.42%)이고, 페르소나 의도를 가진 것은 **3곳(0.03%)** 뿐이었다. 야생의 페르소나
파일은 에이전트 워크스페이스와 개인 저장소에 산다.

파일명만으로 판정하면 오탐률이 93%다(기능 문서의 identity/role, UI 의 Persona 컴포넌트,
UX 페르소나 문서). 그래서 **사람이 의도를 보고 거르는 단계**가 필요하다.

## 단계

1. **검색** — 경로 패턴 5종으로 파일 수집(레코드 수집일 2026-08-09)
2. **포함 기준** — 정체성·역할·목소리·행동 경계를 선언하는 자연어 명세는 넣고, 빌드·테스트
   명령·아키텍처 설명·도구 사용법만 담은 파일은 뺐다. 행동 경계만 선언한 파일도 넣었으므로
   코퍼스의 경계는 정체성만으로 정의할 때보다 넓다
3. **SHA 고정** — 수집 시점에 그 파일을 마지막으로 바꾼 커밋 SHA 를 저장소·경로와 함께 고정
4. **바이트 재수집** — 고정한 SHA 에서 다시 받아 바이트 단위로 대조
   (`refetch` 필드에 결과가 남는다)
5. **라이선스 게이트** — 저장소 전수의 SPDX 를 확인해 재배포 가능 여부를 레코드에 기록

수집 마감 **2026-09-30**.

## 공개본에 없는 것

검색·포함 판정 단계의 후보 수와 스크리닝 기록(2026-09-06 재수집 이전)은 공개본에 없다.
포함 판정 자체의 일치도는 재지 않았고, 포함된 파일은 전부 두 평가자가 독립 코딩했다
(`labels/`).

## 재수집에서 줄어든 레코드

2026-09-06 에 전 파일을 고정 SHA 로 재수집하면서 284건이 281건이 됐다.
280건은 바이트 동일, 1건은 SHA 판으로 교정, 3건은 상류 저장소가 사라져 제외했다.

## provenance 를 고정하는 이유

상류 저장소가 파일을 고치거나 지워도 데이터셋이 흔들리지 않는다. 각 레코드의
`source.commit_sha` 는 그 시점의 내용을 가리키며, 원문이 수록되지 않은 레코드도
이 SHA 로 원본을 직접 받을 수 있다.
